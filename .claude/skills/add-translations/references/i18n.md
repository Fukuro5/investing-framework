# i18n Conventions (next-intl)

## Structure

**One JSON file per locale** — not separate namespace files. This project supports English (default) and Ukrainian:

```
messages/
├── en.json
└── uk.json
```

The two files must always have the same keys/nesting — only the string values differ.

## Top-level Key Groups

Top-level keys reflect the context of where the text is used:

| Pattern | Example |
|---|---|
| `[pageName]Page` | `userProfilePage`, `pricingPage` |
| `[widgetName]Widget` | `newsletterWidget`, `testimonialWidget` |
| `[modalName]Modal` | `confirmDeleteModal`, `contactModal` |
| `common` | Shared labels reused across the app |
| `fields` | Form field labels and placeholders |
| `errors` | Error messages |

## Nested Key Hierarchy

Nested keys reflect the component hierarchy within that group:

```json
{
  "pricingPage": {
    "planCard": {
      "ctaButton": "Get Started"
    }
  }
}
```

Keep nesting shallow — typically no more than 3 levels deep.

## Key Naming

Keys must be **context-based** — describe what the text represents in the UI, not what it says:

✅ Good:
```json
{
  "pricingPage": {
    "title": "Pricing",
    "ctaButton": "Get Started",
    "planCard": {
      "priceLabel": "per month"
    }
  }
}
```

❌ Bad:
```json
{
  "pricingPage": {
    "thisIsThePageTitle": "Pricing",
    "clickHereToGetStarted": "Get Started"
  }
}
```

Common context-based key names: `title`, `subtitle`, `description`, `confirmButton`, `cancelButton`, `submitButton`, `emptyState`, `errorMessage`, `placeholder`, `label`.

## Usage in Components

`useTranslations` works in both Server and Client Components — no `"use client"` or async wrapper needed just to translate:

```tsx
import { useTranslations } from "next-intl";

const t = useTranslations("pricingPage");

<h1>{t("title")}</h1>
<span>{t("planCard.priceLabel")}</span>
<button>{t("common.saveButton")}</button>
```

Outside the component tree (e.g. `generateMetadata`, a Route Handler), use the async equivalent instead:

```tsx
import { getTranslations } from "next-intl/server";

export async function generateMetadata() {
  const t = await getTranslations("pricingPage");
  return { title: t("title") };
}
```

## Rich Text (embedded links, emphasis, etc.)

Don't hardcode JSX wrapping around part of a translated string. Use `t.rich` with tags defined in the message value:

```json
{
  "homePage": {
    "description": "Head over to <templates>Templates</templates> or the <learning>Learning</learning> center."
  }
}
```

```tsx
{t.rich("description", {
  templates: (chunks) => <Link href="/templates">{chunks}</Link>,
  learning: (chunks) => <Link href="/learn">{chunks}</Link>,
})}
```

## Navigation

Use `Link`, `useRouter`, `redirect` from `@/i18n/navigation` (not `next/link`/`next/navigation` directly) so internal links keep the current locale prefix automatically.

## Adding a Locale

Adding a third locale is a deliberate, separate step — not a side effect of adding a key:
1. Add the locale code to `locales` in `i18n/routing.ts`.
2. Create `messages/<locale>.json` with the same key structure as `en.json`.
3. Confirm with the user before doing this — it's a bigger decision than a single translation key.
